## BUG-001：MCP 同步等待阻塞 HTTP 事件循环

位置：`devtoolnext/server.py` 的 `mcp_endpoint`，以及 `devtoolnext/mcp.py` 的 `_tool_wait_for_output`。

异步 HTTP 端点直接调用同步 MCP 处理器；等待工具内部使用线程条件变量进行阻塞等待。因此请求等待设备输出时，同一 HTTP 事件循环无法正常调度其他请求。建连等其他阻塞调用也需要一并检查。

复现：在独立临时目录建立软件回环连接，并发调度真实 MCP 端点函数与一个延迟 50ms 的异步观察任务。MCP 等待期限设为 1 秒，观察任务约在 1.016 秒后才恢复。此复现验证事件循环阻塞；不将它表述为已完成浏览器并发负载测试。

影响：AI 等待期间，界面状态、人工操作或其他客户端请求可能停滞；最长等待可达到工具允许的超时上限。

建议：把阻塞处理移出 HTTP 事件循环，或改为异步任务；同时明确取消、并发限制和任务状态。

验收：一个连接持续等待时，其他状态请求和独立连接仍能响应；取消与超时有效，慢任务不影响串口采集。

## BUG-002：网络远端关闭后，应用连接状态没有结束

位置：`devtoolnext/connectors.py` 的 `ThreadedStream._loop/read`，以及 `devtoolnext/core.py` 的 `DeviceService._read`。

底层网络流遇到 EOF 后设置 `_closed`，但上层 `read()` 仍返回空字节；采集循环将其与普通读取超时同等处理，继续重试。

复现：本机 TCP 服务接受 Telnet 连接，发送 `ready` 后关闭。等待约 300ms 后，底层 `_closed=True`，应用仍为 `connected`，采集线程仍存活。

影响：界面、AI 和日志不能及时识别设备断开；关闭后持续空读存在忙循环风险。CPU 占用程度尚未专门测量。SSH 复用相同流适配逻辑，也需覆盖远端关闭场景。

建议：区分无数据超时、正常 EOF 和读取异常；将终止事件传递到采集服务，收尾记录并通知所有读取者。

验收：Telnet/SSH 正常退出、远端断开和异常断链均能结束采集、更新状态、唤醒等待任务，且不会自动重发命令。

## BUG-003：MCP 文本解码不保持跨记录状态

位置：`devtoolnext/mcp.py` 的 `_record`、`_tool_read_output`、`_tool_wait_for_output`。

当前每条原始记录独立执行 UTF-8 解码并用替换字符处理残缺字节。字符恰好跨记录时，后续拼接已无法恢复原文。终端界面的流式处理不能自动修复 MCP 路径。

复现：将“设备”的 UTF-8 字节切成第一字节与剩余字节两条 RX 记录。原始字节拼接后解码正确，但 MCP 返回文本不正确，等待“设备”也返回未匹配。

影响：AI 读取中文内容失真，基于文本的等待可能误超时。原始 HEX 仍可还原，不应表述为原始数据丢失。

建议：统一定义按连接、方向、编码及游标工作的增量解码策略；明确任意游标落在字符中间时的行为，保留原始证据位置。

验收：UTF-8 多字节字符、GB18030、跨页/跨记录关键词和任意起始游标均有用例；不重复或跳过字节，等待结果与原始数据一致。

## REQ-001：人工与 AI 缺少完整操作所有权

位置：`devtoolnext/core.py` 的 `DeviceService.send`，以及 UI/MCP 的发送与等待入口。

目前有发送互斥，能够串行执行单次写入，但未形成覆盖“发送命令 → 收集响应 → 完成/取消”的设备控制权。发送前的数据库游标也只能表示记录位置，不能证明后面的所有输出均由该命令产生；尚未落库的旧数据同样可能随后出现。

影响：人工或另一 AI 可在前一个任务等待期间插入命令，响应和证据可能混合。

建议：按设备设计控制者、任务、租约、人工接管及取消语义；明确观察者与操作者，以及已发送命令不能撤销的边界。

验收：多个客户端并发操作时不发生命令流程交错；人工接管可以停止后续自动操作，所有动作有来源和状态记录。

## ARCH-001：插件化和离线诊断闭环未完成

当前已经具备串口、Telnet、SSH 的内置字节流适配。尚未形成稳定 SDK、离线插件安装、版本兼容、依赖管理及插件生命周期体系。

最初规划的离线回放、专用故障分析和证据报告也未交付；当前界面已收敛到终端与发送框，不应将日志文件导出等同于分析回放闭环。

建议：先稳定采集与操作接口，再确定最小插件契约。示波器、电源保留自身能力，不强制套用字节流 read/write。诊断闭环按单个真实设备和样本逐步实现。

验收：以后可在不修改核心业务的条件下接入第二类能力；可信插件可以完全离线安装，兼容失败不破坏现有版本；真实样本能重复分析并追溯原始证据。

## SEC-001：SSH 缺少主机指纹确认

位置：`devtoolnext/connectors.py` 的 `SshStream.__init__`。

代码使用 `paramiko.AutoAddPolicy()`，没有建立明确的已知主机加载、首次指纹确认和密钥变化拒绝流程。本轮根据代码确认策略，未进行网络攻击实验。

影响：用户无法据此确认正在连接的 SSH 主机身份。用户名密码脱敏和只读密钥不能代替主机身份校验。

建议：提供受控的 known_hosts 存储与首次确认，记录所信任指纹；密钥发生变化时拒绝自动接受，并给出可核查的提示。

验收：首次连接需要核对指纹；已信任主机可复连；密钥变化被拒绝；AI 不能绕过该流程。
